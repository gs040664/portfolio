主線難度收斂分析

敵方戰力的五版迭代歷程與通關成效驗證

內測數據 · 五版迭代 · 580 關
分析對象主線關卡 1–580
版本數V1 → V5
核心指標標準化戰力
驗證方式內測通關率回測
01

做法

關卡難度由敵我雙方的攻、防、血、迴避、技能倍率等多個維度共同決定，逐項比對無法回答「這一關到底變難還是變簡單」。我把所有屬性標準化成單一的名目戰力作為共同基準，讓跨版本的難度變化可以直接對比，並以內測通關率回測驗證每一版的實際效果。

五個版本、580 關、三項指標：各版本的戰力收斂軌跡、累積通關率的改善、各課群的推進速度。

02

版本迭代歷程

五個版本並非等量調整：V2 只動中後段斜率，V3 因戰鬥系統重構全面下修，V4 針對 200–400 關做區段手術，V5 只做尾段對齊。

V1初始規劃
背景專案啟動時的理論模型，以對數複合函數計算敵方屬性。
調整原因建立主線難度梯次，確保玩家首週有明確成長目標。
結果中後期壓力遠超預期，成為後續四版的基準線。基準

結果與 V4 差異 <1%，屬驗收性微調而非再平衡。定版
03

收斂軌跡

戰力絕對值跨越 6.2 個數量級（1,165 → 18.7 億），改以佔 V1 的百分比呈現，每一版動了哪一段一目了然。

04

通關率改善

每個取樣關卡從 V1 到 V5 的位移，線段長度即為改善幅度。最深的缺口落在 100–200 關，正是 V4 動刀的位置。

01

它不是近似模型，它就是遊戲的戰鬥引擎

大多數關卡模擬器是另寫一套近似公式，誤差從第一行程式碼就開始累積。本模擬器走另一條路：把來源專案的戰鬥 C# 原碼引用式鏈入，編成獨立 console app。觸發技鏈與子觸發技的計算沒有鏡像失真，因為根本沒有鏡像——跑的就是遊戲本身那份程式。

組成性質內容
戰鬥引擎真引擎戰鬥核心模組（回合狀態機、傷害計算、AI、資料結構、階段控制），14,668 行——引用原檔、唯讀、不複製，來源改版自動跟上
Vendor 快照快照從業務混雜大檔抽出的戰鬥閉包（33 型別＋28 成員）。原檔含 2,356 個 UI／帳號編譯錯誤無法直鏈，故抽出；來源改版後重跑抽取腳本即可
Shims替身反作弊型別透傳、UnityEngine 最小替身——只是讓引擎能離開 Unity 跑，不參與任何計算
亂數可控原引擎用時間種；本模擬器改為可控 seed（固定種子環境變數，預設固定 12345）以保回歸確定性

設計目標是改完回填 TSV 就能模擬，不經 Unity 貼表——收斂之後才進 Unity 一次定案。這讓一次設計驗證的成本從「貼表＋開遊戲＋手打一場」降到一行指令。

02

穩定度機制

機制怎麼運作實際紀錄
交棒檔案固定格式變更清單每筆帶 id／欄位／舊值／新值，「改之前的值」同時用來核對現況——對不上就代表資料已被別人動過，直接中止6 種交棒檔案
預設只試跑、不寫入要真的寫入必須另外下指令，讓「不小心寫下去」在結構上不可能發生3 支會動資料的 skill
每階定義中止條件差異項目與預期不符、副本演練結果不對、回頭比對有真差異、設計意圖不明 → 停8 階段皆定義
會影響線上的動作要過四道先拿副本演練 → 覆述一次要做什麼 → 確認帳號正確 → 人工點頭。上次同意不算數，每次都要再問40 次沙箱演練
寫回去之後逐格再比一次直接讀線上正式檔、自動抓表頭位置、不看任何合成欄位，逐格對得上才提交21 次逐格比對
skill 自己也要先通過測試寫完先拿歷史案例全跑一遍、再做盲測回歸，等於替流程本身寫單元測試全案例 ＋ 盲測回歸

兩個已知的不穩定來源：同一份設定存在兩個地方、內容會對不起來（判讀規則寫死為「以實際生效的那一份為準」）、skill 要靠人記得呼叫（忘記就出事的規則改寫成自動檢查與前置條件，不靠人記得）。
